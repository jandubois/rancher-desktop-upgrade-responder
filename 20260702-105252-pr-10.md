## Executive Summary

This upstream merge lands Scarf event forwarding, schema-based request validation, two db-cache fixes, and a dapper-free build. Tests pass and the Helm rename is consistent. But the multi-arch image build is broken: `${TARGETPLATFORM#linux/}` needs a pre-release Dockerfile frontend the file does not pin. Two silent traps also surface — the rules engine reads only the deprecated `ExtraInfo`, and unlisted telemetry keys drop with no log.

Three reviewers ran in parallel; findings were verified against the checked-out SHA, and a live `helm template` render and a `url.PathEscape` probe were run to settle chart and escaping claims. Gemini alone caught the Dockerfile break; Codex and Claude jointly caught the request-data split; Claude alone caught the privacy-doc contradiction and a pre-existing dead-code branch. The findings cluster in three themes: **build/release plumbing** (C1, I3, I5), **silent request-data handling** (I1, I2), and **Scarf robustness** (S1–S3).

## Critical Issues

C1. **Multi-arch image build breaks on an unsupported Dockerfile expansion** — `package/Dockerfile:16` [Gemini 3.1 Pro]

```dockerfile
# syntax=docker/dockerfile:1.7.0
ARG TARGETPLATFORM
ENV ARCH ${TARGETPLATFORM#linux/}
COPY upgrade-responder-${ARCH} /usr/bin/upgrade-responder
```

Bash-style pattern removal (`${var#pattern}`) is supported only under the pre-release `docker/dockerfile-upstream:master` frontend, per Docker's Dockerfile reference — not the stable `docker/dockerfile:1.7.0` this file pins. So `ARCH` does not become `amd64`/`arm64`, and `COPY upgrade-responder-${ARCH}` fails to match the arch-suffixed binaries `scripts/build` produces. The `docker-publish` job builds this file for `linux/amd64,linux/arm64`, so image publishing is blocked. The file was never built locally (Docker daemon was down during review, so a live build could not confirm the exact failure mode).

Fix: use BuildKit's built-in `TARGETARCH`, which yields `amd64`/`arm64` directly.

```dockerfile
ARG TARGETARCH
COPY upgrade-responder-${TARGETARCH} /usr/bin/upgrade-responder
```

## Important Issues

I1. **Rules engine reads only the deprecated `ExtraInfo`, so the advertised `extraTagInfo` migration silently drops version rules** — `rancherdesktop/instanceInfo.go:50,69` [Codex GPT 5.5, Claude Opus 4.8]

```go
// Deprecated: replaced by ExtraTagInfo
ExtraInfo map[string]string `json:"extraInfo"`
...
platformAndArch, ok := checkUpgradeRequest.ExtraInfo["platform"]
```

The merge marks `ExtraInfo` deprecated and makes the telemetry and Scarf paths read the merged `ExtraInfo`+`ExtraTagInfo` (`service.go:515,550` via `MergeStringMaps`). But `NewInstanceInfo` still reads `platform`/`platformVersion` only from `ExtraInfo`, and the RD schema files both keys under `extraTagInfoSchema`. A client that follows the deprecation and sends them as `extraTagInfo` yields an empty parse, so `GenerateCheckUpgradeResponse` falls back to `DefaultVersions` (`service.go:381-384`) — with correct-looking telemetry. Current clients send `extraInfo`, so this is a latent trap, not a live break.

Fix: read from the merged view, mirroring the telemetry path.

```go
extra := utils.MergeStringMaps(req.ExtraInfo, req.ExtraTagInfo)
platformAndArch, ok := extra["platform"]
```

I2. **Schema-dropped tags and fields vanish with no log** — `upgraderesponder/service.go:135-152` [Claude Opus 4.8, Gemini 3.1 Pro]

```go
schema, ok := s.RequestSchema.ExtraTagInfoSchema[key]
if !ok {
    return false   // key dropped, nothing logged
}
```

The old path stored every `extraInfo` key as a tag; the new path keeps only schema-listed keys. When a key is missing from the schema, `ValidateExtraInfo` returns false with no log, and the value-level check logs only at Debug (`Schema.Validate`, `service.go:106`) — invisible at the default Info level. An operator who omits a schema entry loses that telemetry dimension with zero signal, on the tool whose whole purpose is telemetry. The chart's default `requestSchema` (`chart/values.yaml:26-33`) defines only `appVersionSchema`, so a stock deploy drops all extra tags.

Fix: log dropped keys at a visible level, and warn at startup when the RD-relevant keys are absent from the loaded schema.

I3. **CI never builds or publishes the fork's default branch** — `.github/workflows/build.yml:4-7` [Codex GPT 5.5, Claude Opus 4.8]

```yaml
  push:
    branches:
    - master
    - longhorn
    - v*
```

The fork's default branch is `rancher-desktop`, absent from the push filter, so a push to it runs neither `build` nor the `build_push_image` job that publishes the `<branch>-head` image. Pull requests still get CI and `v*` tag pushes still publish releases, so the gap is post-merge mainline coverage, not all CI. The job also targets `longhornio/upgrade-responder` and needs `DOCKER_USERNAME`/`DOCKER_PASSWORD`/`CODECOV_TOKEN`, and `mergify.yml` keys on `@longhorn/maintainer` and `renovate[bot]` — all longhorn-specific.

Fix: decide fork intent — add `rancher-desktop` to the triggers and wire fork secrets, or drop the image-push and mergify rules that do not apply here.

I4. **README privacy claim contradicts Scarf IP forwarding** — `README.md:211`, `upgraderesponder/scarf.go:99` [Claude Opus 4.8]

```go
req.Header.Set("X-Scarf-IP", clientIP)
```

`README.md:211` states the server "doesn't store any information that can be potentially used to identify the client... including IP address," and line 429 repeats it. Once `--scarf-endpoint` is set, `sendEventSync` forwards the client's public IP to scarf.sh in `X-Scarf-IP`. The server itself still stores no IP, so the claim is narrowly true, but a privacy-conscious reader would not expect it to omit a new third-party data flow. The forwarding is intentional (Scarf uses IP for geo), so the fix is documentation.

Fix: qualify the privacy statement for the Scarf-enabled case, and note in the `--scarf-endpoint` docs that enabling it transmits the client IP to scarf.sh.

I5. **Local run scripts call a binary the build no longer produces** — `rancherdesktop/run.sh:3` [Codex GPT 5.5]

```sh
$REPO_ROOT/bin/upgrade-responder --debug start \
```

`scripts/build` now emits `bin/upgrade-responder-amd64` and `-arm64` only, but `run.sh:3` and the README run commands (`README.md:244,439`) still invoke `bin/upgrade-responder`. After `make build`, the documented local-run flow fails with "not found."

Fix: after building both arches, copy the host-arch binary to `bin/upgrade-responder`, or update the scripts and docs to select the suffixed name.

## Suggestions

S1. **`substituteTemplateVars` uses `url.PathEscape`, which leaves query metacharacters unescaped** — `upgraderesponder/scarf.go:145` [Claude Opus 4.8]

```go
return url.PathEscape(value)
```

`PathEscape` escapes path segments but passes `&` and `=` through (verified: `PathEscape("a&b=c") == "a&b=c"`). A Scarf template that places a client-controlled variable in a query string — `https://scarf.sh/e?v={version}` — lets a crafted `appVersion` such as `x&admin=1` inject query parameters. Values are validated for type and length but not content, and the reserved `{version}` comes straight from `req.AppVersion`.

Fix: escape by position, or use `url.QueryEscape` for values destined for query strings; at minimum, document that templates must place variables in path segments only.

S2. **Scarf response body is closed without draining, defeating connection reuse** — `upgraderesponder/scarf.go:121-127` [Gemini 3.1 Pro]

```go
if err := resp.Body.Close(); err != nil {
```

Go returns a connection to the pool only when its body is read to EOF. `closeResponseBody` closes without draining, so the shared `httpClient` opens a fresh connection per event. With Scarf enabled under sustained load, this churns sockets toward ephemeral-port exhaustion. Off by default, so this is a scaling caution.

Fix: `io.Copy(io.Discard, resp.Body)` before `Close`.

S3. **Scarf sends spawn one unbounded goroutine per request** — `upgraderesponder/scarf.go:71` [Claude Opus 4.8]

```go
go func() {
    if err := s.sendEventSync(templateVarsCopy, clientIP); err != nil {
```

`SendEvent` launches a goroutine — and one HTTP call per endpoint — for every valid request, with no bound. If scarf.sh is slow (default 30s timeout), goroutines and sockets accumulate under load. Off by default.

Fix: gate sends through a bounded worker pool or semaphore, dropping and counting events when saturated.

S4. **Blocking send on the unbuffered `syncChan` piles up request goroutines** — `upgraderesponder/db-cache.go:102-104` [Gemini 3.1 Pro]

```go
if needToSync {
    c.syncChan <- struct{}{}
}
```

Once the cache exceeds `CacheSize`, every `AddPoint` attempts a blocking send on the unbuffered `syncChan`. While the consumer is inside `Sync()`, request goroutines stack up waiting to enqueue a wakeup that a single pending signal already covers.

Fix: use a non-blocking `select` send with a `default` branch.

S5. **`multierr` shim wraps a one-line `errors.Join`** — `upgraderesponder/scarf.go:20-27` [Claude Opus 4.8]

```go
func (multierrType) Append(errs ...error) error { return stdErrors.Join(errs...) }
```

The shim reproduces a third-party API name for a single stdlib call, and the `stdErrors` alias exists only to feed it.

Fix: accumulate into a `[]error` and call `errors.Join(errs...)` once, dropping the type, the package var, and the alias.

## Design Observations

### Concerns

- **Two code paths read the same request data from different sources (future)** [Codex GPT 5.5, Claude Opus 4.8]. The rules engine keys off `ExtraInfo` alone; telemetry and Scarf key off the schema-filtered merge of `ExtraInfo` and `ExtraTagInfo`. This split is the structural root of I1 and invites drift each time a new consumer of request data appears. A single normalization at ingress — resolve one canonical map, honor the deprecation once, hand it to every consumer — collapses the read sites and removes the bug class.
- **`Sync()` holds the cache lock across the network write (future, pre-existing)** [Gemini 3.1 Pro]. `db-cache.go:64-88` keeps `c.Lock()` for the whole retry loop, including `InfluxClient.Write`, so `AddPoint` blocks while a flush is in flight. This PR mitigates it — retries drop from 5 to 2 and `influxClientTimeOut = 10s` bounds the hold — but the lock still spans I/O. A future change could swap the batch under the lock and write outside it.
- **`db-cache.go` dead "dropped batch" branch (future, pre-existing)** [Claude Opus 4.8]. In `Sync()` the guard `else if i < maxSyncRetries` is always true inside `for i := 0; i < maxSyncRetries; i++`, so the "Dropped the batch points" log at `db-cache.go:79` never runs. On persistent InfluxDB failure the batch is discarded with only per-retry Debug logs, hiding real data loss. The condition should be `i < maxSyncRetries-1`.

### Strengths

- **Scarf init trims, deduplicates, and disables cleanly, and copies template vars before the goroutine (in-scope)** [Codex GPT 5.5] — request handling stays isolated from later map mutation.
- **Schema-driven filtering caps tag cardinality at the server boundary (in-scope)** [Codex GPT 5.5] — unknown keys drop before InfluxDB rather than becoming uncontrolled series.
- **The db-cache changes fix the real bugs (in-scope)** [Claude Opus 4.8] — releasing the lock before signalling `syncChan` removes the deadlock, the empty-batch guard also blocks a nil-client write, and the 10s InfluxDB timeout bounds the hang.

## Review Process Notes

### Skill improvements

- When a Dockerfile uses bash-style parameter expansion (`${var#pattern}`, `${var%pattern}`, `${var/pattern/replacement}`), verify the pinned `# syntax=docker/dockerfile:` frontend supports it. Per Docker's Dockerfile reference these forms are available only under the pre-release `docker/dockerfile-upstream:master` frontend, not stable `1.x` tags, so a stable pin silently fails to strip or substitute and a downstream `COPY`/`RUN` using the result breaks. Prefer BuildKit's predefined `TARGETARCH`/`TARGETOS` over hand-stripping `TARGETPLATFORM`.

- On any path that collects or records data, when a change adds validation or filtering that discards input (schema mismatch, unknown key, failed parse), check that each discard is observable at the default log level. A drop logged only at Debug, or not logged at all, hides operator misconfiguration on exactly the path whose purpose is to capture data.

- When a struct field is deprecated in favor of a replacement, enumerate every read site of the deprecated field and confirm each one also reads the replacement (or a merged view of both). A partial migration leaves the deprecated field load-bearing in precisely the paths that were not updated, so a client that adopts the replacement silently loses behavior those paths drive.

- When reviewing a merge from an upstream into a fork, check that inherited CI triggers, secrets, image targets, bot/merge rules, and hard-coded branch names match the fork's own names. Upstream config keyed on the upstream's default branch, org handles, or registry silently no-ops or fails in the fork — pull-request CI can still pass while post-merge builds and publishes never fire.

### Repo context updates

- [repo] This repository is a fork of `longhorn/upgrade-responder` that periodically merges the upstream. Its default branch is `rancher-desktop`, not `master`. Treat merge PRs from upstream as reconciliations: the fork-specific surface is `rancherdesktop/` (a rules engine that replaces the upstream `VersionMap`), the Helm chart's image repository, and CI/config that must be checked against fork names rather than longhorn's.

- [repo] Local development runs through `rancherdesktop/run.sh` plus `rancherdesktop/testdata/` (response config and request schema); the Helm chart is a separate, less-exercised path. Verify chart changes with a live `helm template` render, since the run.sh smoke test does not cover them.

#### Critical Issues

C1. **Invalid Dockerfile variable substitution breaks multi-arch build** — `package/Dockerfile:14-16` (critical, regression)

```dockerfile

    exit 1; \
    fi

COPY GeoLite2-City.mmdb /usr/share/
```

Dockerfile `ENV` instructions do not support bash-style suffix/prefix removal. The syntax `${TARGETPLATFORM#linux/}` evaluates to that exact literal string, causing the `COPY` instruction to fail because `upgrade-responder-${TARGETPLATFORM#linux/}` does not exist.

-COPY upgrade-responder-${ARCH} /usr/bin/upgrade-responder
+COPY upgrade-responder-${TARGETARCH} /usr/bin/upgrade-responder
