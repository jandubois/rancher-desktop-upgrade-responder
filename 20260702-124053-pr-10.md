## Review Process Notes

### Skill improvements

- When a change gates a side-effect (publish, deploy, tag, delete, release) by ref, branch, repository, or event, enumerate every trigger that still satisfies the condition — tags as well as branches, forks as well as the upstream — not just the one the change touched. A gate that correctly excludes one trigger routinely leaves a sibling trigger firing the side-effect in a context where it is wrong (a branch exclusion that leaves the tag path publishing, an environment guard that leaves the cron path deploying). Trace each arm of the boolean to the effect it still permits.

- When a finding claims a lint, format, or CI gate fails, run that gate at the version the project pins before trusting it. Check the Dockerfile, CI workflow, or lockfile for the pinned tool version and reproduce with that exact version. Linters change their default rule sets and default exclusions across major versions, so a local run at a newer version produces findings the project's CI does not enforce — reporting them as "CI breaks" is a false positive.

### Repo context updates

- [repo] CI validation (`make validate`) runs `golangci-lint` pinned to the version in `Dockerfile` (`GOLANGCI_LINT_VERSION`). Reproduce lint findings at that version — a newer local golangci-lint drops the old default exclusions and flags `errcheck` on `defer x.Close()` patterns that CI does not fail on.

- [repo] The fork's Helm chart pulls its image from `ghcr.io/rancher-sandbox/rancher-desktop-upgrade-responder`, but the inherited `build.yml` publishes to `longhornio/upgrade-responder`. The fork's own image-publish path is deliberately unbuilt (a separate decision); treat any publish trigger that fires on the fork (branch or tag) as a gap until the fork's registry is wired.

```yaml
    # The rancher-desktop branch runs CI but skips this job: it publishes to
    # longhornio, whereas the fork's image lives in ghcr.io/rancher-sandbox.
    if: ${{ (startsWith(github.ref, 'refs/heads/') && github.ref != 'refs/heads/rancher-desktop') || startsWith(github.ref, 'refs/tags/') }}
```

The condition correctly skips the `rancher-desktop` branch to prevent publishing to `longhornio` from the fork. However, the tag condition (`startsWith(github.ref, 'refs/tags/')`) applies to all tags, including those pushed to the fork. Tagging a release on the fork will trigger this job, which will likely fail when `docker/login-action` finds empty `DOCKER_USERNAME` secrets. If the secrets were present, it would attempt to publish the fork's image to the upstream `longhornio` registry.

Fix: Gate the job strictly to the upstream repository.
```diff
-    if: ${{ (startsWith(github.ref, 'refs/heads/') && github.ref != 'refs/heads/rancher-desktop') || startsWith(github.ref, 'refs/tags/') }}
+    if: ${{ github.repository == 'longhorn/upgrade-responder' && (startsWith(github.ref, 'refs/heads/') || startsWith(github.ref, 'refs/tags/')) }}
```

I2. **Schema-dropped tags/fields vanish with no log at default level (upstream)** — `upgraderesponder/service.go:516-520` (important, gap)

```go
	for k, v := range extraTagInfo {
		if s.ValidateExtraInfo(k, v, extraInfoTypeTag) {
			tags[utils.ToSnakeCase(k)] = v
		}
	}
```

If `ValidateExtraInfo` returns false, the tag is silently ignored (it only logs at the `Debug` level). In production, missing schema keys will cause clients' telemetry data to disappear silently, making it difficult to detect misconfigurations.

Fix: Log a warning when dropping telemetry data due to schema validation failures.

I3. **README privacy claim contradicts Scarf client-IP forwarding (upstream)** — `README.md:211`, `upgraderesponder/scarf.go:99` (important, gap)

```markdown
Upgrade Responder server doesn't store any information that can be potentially used to identify the client that makes the request, including IP address.
```

The README explicitly claims client IPs are not stored or tracked. However, `X-Scarf-IP` directly forwards the client's public IP to a third-party service (Scarf). 

Fix: Update the README to disclose the IP forwarding when Scarf endpoints are configured.

#### Suggestions

S1. **Scarf uses PathEscape instead of QueryEscape (upstream)** — `upgraderesponder/scarf.go:142` (suggestion, gap)

```go
		if value, ok := vars[key]; ok {
			return url.PathEscape(value)
		}
```

If a substituted variable is placed in the query string of a Scarf endpoint template, `url.PathEscape` leaves query metacharacters like `&` and `=` unescaped, potentially breaking the constructed URL.

Fix: Use `url.QueryEscape` instead.

S2. **Scarf response body closed without draining (upstream)** — `upgraderesponder/scarf.go:121` (suggestion, gap)

```go
func closeResponseBody(resp *http.Response) {
	if resp != nil && resp.Body != nil {
		if err := resp.Body.Close(); err != nil {
```

Failing to drain the response body before closing prevents the `http.Client` from reusing the underlying TCP connection, leading to a new TCP connection setup for every Scarf event.

Fix: Add `io.Copy(io.Discard, resp.Body)` before closing the body.

S3. **Unbounded goroutines for Scarf events (upstream)** — `upgraderesponder/scarf.go:71` (suggestion, gap)

```go
	go func() {
		if err := s.sendEventSync(templateVarsCopy, clientIP); err != nil {
```

A new goroutine is spawned for every valid request to `SendEvent`. Under high load, this could exhaust server resources given the default 30-second HTTP timeout.

Fix: Use a worker pool or bounded concurrency for event forwarding.

S4. **Blocking send on unbuffered `syncChan` (upstream)** — `upgraderesponder/db-cache.go:104` (suggestion, gap)

```go
	if needToSync {
		c.syncChan <- struct{}{}
	}
```

Because `syncChan` is unbuffered, `AddPoint` blocks if `Sync()` is already running. This stalls incoming requests while the background database write completes.

Fix: Buffer the channel or use a non-blocking send (`select { case c.syncChan <- struct{}{}: default: }`).

S5. **`multierr` shim is unnecessary (upstream)** — `upgraderesponder/scarf.go:20-27` (suggestion, gap)

```go
type multierrType struct{}

var multierr = multierrType{}

func (multierrType) Append(errs ...error) error {
	return stdErrors.Join(errs...)
}
```

A custom `multierrType` is implemented just to wrap `errors.Join`, adding indirection without any additional behavior.

Fix: Drop `multierrType` and call `errors.Join` directly.

### Design Observations

#### Concerns
- **`Sync()` holds cache lock across network write (upstream)**: `upgraderesponder/db-cache.go:64` locks the entire cache while making a synchronous HTTP request to InfluxDB. This effectively pauses all incoming upgrade requests attempting to call `AddPoint` during the network round-trip. `Sync()` should extract the `BatchPoints`, replace the cache buffer, and release the lock *before* initiating the network request. `(in-scope)`

### Testing Assessment

1. **Schema validation rejection data**: There are no tests verifying that invalid tag/field entries are correctly stripped out of the telemetry payload before the InfluxDB point is built.
2. **Scarf HTTP client timeout behavior**: The integration tests do not simulate delayed upstream Scarf responses to verify that the timeouts enforce correctly.

### Documentation Assessment

The README requires an update to align with the new Scarf IP forwarding behavior (see finding I3).
