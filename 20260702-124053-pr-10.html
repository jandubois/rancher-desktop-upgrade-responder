Review Process Notes ¶

Skill improvements ¶

  • When a change gates a side-effect (publish, deploy, tag, delete, release) by ref, branch, repository, or event, enumerate every trigger that still satisfies the condition — tags as well as branches, forks as well as the upstream — not just the one the change touched. A gate that correctly excludes one trigger routinely leaves a sibling trigger firing the side-effect in a context where it is wrong (a branch exclusion that leaves the tag path publishing, an environment guard that leaves the cron path deploying). Trace each arm of the boolean to the effect it still permits.
  • When a finding claims a lint, format, or CI gate fails, run that gate at the version the project pins before trusting it. Check the Dockerfile, CI workflow, or lockfile for the pinned tool version and reproduce with that exact version. Linters change their default rule sets and default exclusions across major versions, so a local run at a newer version produces findings the project's CI does not enforce — reporting them as "CI breaks" is a false positive.

Repo context updates ¶

  • [repo] CI validation (make validate) runs golangci-lint pinned to the version in Dockerfile (GOLANGCI_LINT_VERSION). Reproduce lint findings at that version — a newer local golangci-lint drops the old default exclusions and flags errcheck on defer x.Close() patterns that CI does not fail on.
  • [repo] The fork's Helm chart pulls its image from ghcr.io/rancher-sandbox/rancher-desktop-upgrade-responder, but the inherited build.yml publishes to longhornio/upgrade-responder. The fork's own image-publish path is deliberately unbuilt (a separate decision); treat any publish trigger that fires on the fork (branch or tag) as a gap until the fork's registry is wired.
